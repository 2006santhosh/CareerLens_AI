# AI Methodology

## Where AI is used — and, just as importantly, where it isn't

CareerLens AI follows one rule throughout: **the LLM never controls scoring**. All numbers a student
sees (skill level, gap, priority, readiness) come from deterministic formulas over data in the
database. AI is used only for two things:

1. **Resume/skill extraction** from unstructured text (`AIService.extract_resume`)
2. Nothing else in the current build — even gap explanations are Python string templates
   (`AIService.explain_gap`), not LLM calls, so they are instant, free, and 100% reproducible.

## Skill extraction

- **Live mode** (`AI_MODE=live`): sends the resume text plus the full canonical skill list to the
  Anthropic Messages API with a strict system prompt (`EXTRACTION_SYSTEM_PROMPT` in `ai_service.py`)
  that instructs the model to (a) extract only skills supported by the text, (b) map them to the
  supplied canonical list, (c) return only valid JSON matching a fixed schema, and (d) never invent
  skills. The response is parsed and every returned skill name is checked against the canonical skill
  set (case-insensitive) — anything the model returns that isn't in that set is silently dropped. This
  is the schema validation described in the brief ("never trust raw AI output blindly").
- **Demo mode** (`AI_MODE=demo`, or automatic fallback if the live call fails for any reason — bad
  key, network error, malformed JSON): a deterministic keyword/word-boundary matcher scans the resume
  text against the canonical skill list, assigns a confidence score based on how many times a skill is
  mentioned, and extracts projects/certifications/education via simple heading/keyword heuristics. This
  guarantees the demo never fails because of API limits, connectivity, or an invalid key.

## Semantic mapping

Extracted skill names are matched to the canonical `Skill` table by exact name (live mode) or via the
`SkillAlias` table for common synonyms (e.g. a resume that says "Postgres" maps to the canonical
"PostgreSQL" skill through an alias row). This keeps the mapping step transparent and debuggable rather
than relying on an embedding similarity search, which was judged unnecessary complexity for the
current skill catalog size — see "Future improvements" in the README for where pgvector-based semantic
matching would fit if the catalog grows much larger or noisier.

## Gap calculation (fully deterministic)

For each required skill on the target career:

```
Gap      = max(0, RequiredLevel - CurrentLevel)
Priority = Gap × ImportanceWeight × DependencyImpact × EvidenceConfidenceAdjustment
```

- `ImportanceWeight`: High = 1.5, Medium = 1.0, Low = 0.6 (from the career's required-skill importance)
- `DependencyImpact`: `1 + 0.25 × min(downstream_skill_count, 4)` — a skill that unlocks more
  downstream skills (per the `SkillDependency` graph) is weighted higher
- `EvidenceConfidenceAdjustment`: skills already backed by stronger evidence get a *lower* multiplier
  (verified = 0.6×, assessed = 0.8×, evidence found = 0.9×, self-reported/none = 1.0×) — the intuition
  being that a verified skill is less urgent to re-address even if its gap isn't fully closed
- All priority scores within one gap analysis are then normalized to 0–100 so they're comparable

Every gap comes with a plain-English `reason` (skill name, target vs. current level, importance, and
which downstream skills it unlocks) — never a bare number.

## Prioritization & roadmap generation

The roadmap engine takes every skill with `gap > 0`, builds a subgraph of just those skills'
prerequisite relationships (`SkillDependency`), and performs a topological sort: a skill can only be
scheduled once all of its in-set prerequisites are already scheduled. Ties among "ready" skills are
broken by the gap-engine's priority score (highest first). This guarantees, for example, that Linux is
always scheduled before Docker, and Docker before Kubernetes, for any student — validated by
`test_roadmap_respects_prerequisite_order` in the pytest suite.

Each roadmap item's "why / what to learn / what to build / how to prove it" text is generated by
template functions (not an LLM call) so the roadmap can be regenerated instantly and deterministically
every time new evidence comes in.

## Readiness calculation

```
Overall = 0.30 × TechnicalSkills + 0.20 × ProjectEvidence + 0.20 × AssessmentPerformance
        + 0.20 × SkillCoverage   + 0.10 × Verification
```

Each component and its weight is returned to the frontend as an `explanation` dict, so the UI can (and
does) show *why* the number is what it is rather than a mysterious percentage. Readiness explicitly
never claims to predict job placement — see the "Career Readiness Engine" note in the project brief and
the disclaimer on the Settings page.

## Verification state machine

```
self_reported → evidence_found → assessed → verified
```

- `evidence_found`: at least one of resume/project/GitHub/certification evidence exists
- `assessed`: the skill has at least one assessment attempt
- `verified`: the skill has a strong assessment result (≥70%) **and** at least one other evidence
  signal — a claim alone, or an assessment alone, is never enough to reach Verified

## Limitations

- Demo-mode extraction is keyword-based, so it will miss skills mentioned only via synonyms not in the
  `SkillAlias` table, and can over-match common words that happen to coincide with a skill name.
- Live-mode extraction quality depends on the underlying model and is capped at whatever the canonical
  skill list contains — it will never invent a skill outside that list, which is a deliberate
  trade-off (precision over recall).
- The current assessment bank (6 skills) is far smaller than the full 76-skill catalog; skills without
  an assessment can still reach `evidence_found` but not `assessed`/`verified` via a quiz.
